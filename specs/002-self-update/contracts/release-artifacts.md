# Release-Pipeline Contract: Artifacts & Workflow

**Feature**: 002-self-update | **Date**: 2026-05-30

This is the contract for the release pipeline as observed from the
outside: which workflow triggers, what assets it produces, and what
the release body looks like. Implementation details (which YAML files
contain what) live in tasks.md.

## Trigger

- **Event**: `push` to a tag ref matching `refs/tags/v*.*.*` (with
  optional `-<prerelease>` and `+<build>` suffixes).
- **Branch source**: only tags whose commit is reachable from `main`
  (the default branch). Tags pushed to other branches or refs are
  silently ignored.
- **Fork safety**: workflow contains
  `if: github.repository == 'buildoutinc/injector'` on every job.
  Workflows from forks therefore never run.
- **Tag malformed**: if a tag ref starts with `v` but does not match
  semver, the workflow's first job (`validate`) fails fast with a
  clear message and no release is produced. (FR-020.)
- **Maps to**: FR-015, FR-020

## Produced GitHub Release

For tag `vX.Y.Z`, the workflow creates a GitHub Release named `vX.Y.Z`
attached to that tag with these properties:

### Release body (changelog)

- Generated by `git-chglog --next-tag vX.Y.Z` using the previous tag
  on `main` as the lower bound.
- Sections (in order, omitted when empty):
  - `## Features` — commits starting with `feat:` / `feat(scope):`
  - `## Fixes` — commits starting with `fix:` / `fix(scope):`
  - `## Performance` — `perf:` (optional)
  - `## Refactor` — `refactor:`
  - `## Documentation` — `docs:`
  - `## Other Changes` — every commit that didn't match a typed prefix
    (FR-017). Never empty unless every single commit since the
    previous tag had a Conventional Commit prefix.
- Each entry: `- {subject} ({short SHA})`.

### Release assets

| Filename | Format | Contents |
|----------|--------|----------|
| `inject_<X.Y.Z>_linux_amd64.tar.gz` | tar+gzip | `inject` binary, root |
| `inject_<X.Y.Z>_linux_arm64.tar.gz` | tar+gzip | `inject` binary, root |
| `inject_<X.Y.Z>_darwin_amd64.tar.gz` | tar+gzip | `inject` binary, root |
| `inject_<X.Y.Z>_darwin_arm64.tar.gz` | tar+gzip | `inject` binary, root |
| `checksums.txt` | plain text | SHA-256 of each archive, GoReleaser default format |

The archive name pattern is `inject_<version>_<os>_<arch>.tar.gz` (no
`v` prefix on the version field — GoReleaser strips it from
`{{ .Version }}`). The library's regex matcher detects `_<os>_<arch>`
inside this name, so the upgrade flow finds the right asset.

The binary inside each archive has its `version` symbol linked to the
exact tag string (with the `v` prefix, e.g. `v0.3.0`) via
`-ldflags "-X main.version=v{{ .Version }}"`.

- **Maps to**: FR-016, FR-017, FR-018, FR-019

## Idempotency / re-runs (FR-021)

- GoReleaser uses `--clean` to wipe `dist/` per run.
- Uploading an asset that already exists on the release returns
  HTTP 422; the workflow does not catch this — the job fails with a
  non-zero exit and the maintainer is alerted. The existing release
  is **not** mutated.
- Re-running the workflow on the same tag therefore either succeeds
  (if the release didn't already exist) or fails loudly (it did).
  Never a silent duplicate.

## Pre-releases (`vX.Y.Z-<prerelease>`)

- Workflow detects the `-` suffix and passes `goreleaser release
  --skip=announce` plus `prerelease: true` in `.goreleaser.yaml`'s
  `release` block (already set to `auto`, which infers from the tag).
- GitHub Release is marked "Pre-release", hidden from the "Latest"
  badge.
- `inject upgrade` ignores it by default; `inject upgrade
  --pre-release` includes it.

## Validation steps before publish

1. **Tag shape**: validate `^v[0-9]+\.[0-9]+\.[0-9]+(-[A-Za-z0-9.-]+)?(\+[A-Za-z0-9.-]+)?$`.
   Fail otherwise (FR-020).
2. **Workflow source check**: `if: github.repository == 'buildoutinc/injector'`.
3. **goreleaser check** (`goreleaser check`) before publish to catch
   config drift.
4. **Build**: cross-compile four target archives + checksums.
5. **Publish**: upload to GitHub Release attached to the tag with the
   `git-chglog`-generated body.

## Quickstart of a release

```bash
git checkout main
git pull
# create some commits with Conventional Commit prefixes
git tag -a v0.3.0 -m "v0.3.0"
git push origin v0.3.0
# … wait for release.yml to finish; verify Release in the GitHub UI
```

A subsequent `inject upgrade` on any developer machine running v0.2.x
must succeed end-to-end.
